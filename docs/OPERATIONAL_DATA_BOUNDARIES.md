# Operational Data Boundaries

## Purpose

This document defines the boundary between source-controlled platform assets and
operational runtime state for Security Intelligence Hub.

## 1. Source-Controlled Assets

These are expected to remain tracked:

- Platform source code under src/
- Deterministic tests under tests/
- Deterministic fixtures under tests/fixtures/
- Architecture/governance/contracts documentation under docs/
- Validators and quality gates under scripts/ and tests/
- Curated run scaffolding and examples:
  - runs/README.md
  - runs/.gitkeep and stage/log/manifest .gitkeep placeholders
  - runs/manifests/example_run_manifest.json
- Benchmark contract scaffolding under data/history/benchmarks/

## 2. Operational Runtime State

These are operational outputs generated by executions and are isolated from
source control going forward:

- runs/logs/* (except .gitkeep)
- runs/manifests/RUN-* artifacts
- runs/stage_manifests/RUN-* artifacts
- data/current/*
- data/history run partitions and runtime indexes

## 3. Generated Data Policy

Generated operational outputs are not continuously tracked in git.
They may be created locally for execution, validation, and replay, but are
isolated via ignore policy.

## 4. Raw Provider Payload Policy

Raw provider intake payloads under incoming/ess/ are operational evidence and
are isolated from source control by default.

Deterministic lane placeholders (.gitkeep) remain tracked to preserve ingestion
path contracts.

## 5. Fixture Policy

Deterministic fixtures under tests/fixtures/ remain tracked and versioned.
They are part of the reproducible testing contract and are not operational
runtime noise.

## 6. Current vs Historical Data Philosophy

- data/current represents mutable latest-state outputs.
- data/history runtime partitions represent immutable run evidence.

Both are operational data layers and are isolated from ongoing source tracking,
while historical milestone commits preserve prior lineage snapshots.

## 7. Why Runtime Partitions Are Operational State

Partition files are execution-emitted artifacts tied to specific run_id and
snapshot_date values. They are essential for runtime evidence and replay, but
continuous tracking in git introduces repository churn and noise.

## 8. Why Fixtures Remain Tracked

Fixtures are curated, deterministic, and intentionally stable. They provide a
repeatable baseline for validation and regression tests, unlike runtime-emitted
artifacts.

## 9. Future Storage Evolution Possibilities

Operational runtime storage may evolve toward:

- object storage with retention policies
- artifact registries with lifecycle controls
- data lake partition catalogs
- signed evidence bundles for audit workflows

These options preserve lineage without polluting source control.

## 10. Milestone Lineage Preservation Rationale

Previously committed milestone runtime evidence is preserved in git history for
traceability. This isolation pass does not rewrite history; it only transitions
future operational state away from active tracking.
